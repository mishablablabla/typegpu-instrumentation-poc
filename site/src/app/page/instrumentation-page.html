Tooling

See what your TypeGPU application is doing.

The instrumentation layer turns a running TypeGPU program into a stream of plain-data events (resources, bind groups, pipelines, shader diagnostics, device errors, teardown) and a snapshot of what is alive. It has no UI and no framework dependency: it is a reusable foundation that consoles, reports, test helpers and developer tools can be built on.

It observes what goes through TypeGPU's own paths. It does not observe everything that happens inside WebGPU, GPU execution time, or raw WebGPU calls you make yourself.

The debugging problem#

A TypeGPU program can fail in two different layers. A TypeGPU failure happens while TypeGPU builds the shader: a slot without a value, a missing bind group. The browser never sees it. A WebGPU failure happens after: the generated WGSL is rejected, a pipeline is invalid, the device is lost. The browser reports it as text about code you did not write. TypeGPU itself installs no error scopes, no uncapturederror listener and no device-loss handler, so that context is left to you.

Chrome is already good at the second case, so the point is not "the browser says nothing". The two panes below are real captures of the same program, examples/broken-shader.ts, on an Apple M3 Pro in Chrome 156.

Architecture#

Hooks inside TypeGPU's core report what happened; an optional hub keeps a bounded history and a snapshot; everything above the event contract is an independent consumer. The contract is the integration boundary, so the core carries no UI, DOM, framework, extension or MCP code.

What must stay framework-independent

  • The hook sites and the sink contract (types only in core), the hub, the history, the snapshot and the event schema.
  • Anything that turns events into text, files or pixels belongs to an adapter or consumer, outside the package. The "named repeatedly" notes in the churn scenario are a consumer's interpretation, not the core's.

Details: architecture and lifecycle, including the alternatives that were evaluated (device-scoped registry, lazy import(), a separate entry point, a device-level tap, a global hook).

Ordering, identifiers, errors, limits

  • Order. seq is contiguous per root, starting at 1. Every listener receives events in seq order, even when a listener calls back into TypeGPU (nested events are queued). Order between asynchronous events is not promised beyond: shader-diagnostics follows its creation event; a device-error may come before or after it.
  • Correlation. A pipeline's id names its core, so all with() handles share it and a retry after a failure keeps it. shader-diagnostics.pipelineId points to it. A device-error carries no pipeline id: browsers give text, not an object.
  • Errors. Failures are events with errorType and message; the application still receives the identical error. A subscriber that throws, even an unprintable value, never reaches the app or other subscribers.
  • History. Bounded by count (default 256) and by an estimate of bytes (default 4 MiB), newest always kept; the last 16 creation failures and the device-loss event are pinned in snapshot.retainedFailures.

Full definition, the guarantee-to-test table and the deviations found by audit: EVENT-CONTRACT.md.

Is there a gap?#

Short answer, from primary sources and a control experiment (full research): a narrow one. Nothing in the three scenarios is unique at the level of information. What is unique is who can know it from where: TypeGPU's own facts (when a pipeline was created and how, failures that never reach WebGPU, per-pipeline counts) exist only inside TypeGPU.

ScenarioWhat the layer addsHonest classification
Broken shaderAttribution to the TypeGPU pipeline and trigger; structured compiler position; retention{{ info['broken-shader'].classificationLabel }}
Resolution errorAn event for something the browser never sees; survives a swallowed exception{{ info['resolve-error'].classificationLabel }}
Per-frame churnGrouping by TypeGPU label, CPU resolve time, teardown leftovers{{ info['per-frame-churn'].classificationLabel }}

Against existing tools

  • Runtime Inspector MCP is not a duplicate. It is an offline, one-shot validator: it runs your module in its own headless Chromium with frame loops, submits and pipeline initialisation stubbed, so it does not observe a live app. Complement or unrelated on the evidence read; whether it could consume this stream is unproven.
  • WebGPU Inspector is the real competitor for raw WebGPU (frame capture, object list, memory, GPU time). The layer must not claim any of that; GPU labels are the join key.
  • Upstream has open work on source maps and a device-error item (issue 2935) that may make shader-diagnostics and device-error partly redundant. No demand signal was found in upstream issues or discussions.

Assertions as data: "no pipeline-creation-failed, no device-error, nothing alive at teardown" in a test or CI run, without hand-wiring error scopes or reaching TypeGPU's internal shader modules. That is a reasoned claim, not a measured demand.
